Java IO框架笔记

体系结构：装饰器模式与流的设计哲学

字节流与字符流的分工

Java IO 框架包含两套独立的体系：InputStream / OutputStream（字节流）和 Reader / Writer（字符流）。字节流处理二进制数据（如图片、音频），字符流专门处理文本数据。

两套体系之间的关系：字符流是对字节流的封装，内部通过 InputStreamReader 和 OutputStreamWriter 完成字节到字符的转换，而这个转换过程正是编码处理的核心。当文件编码与系统默认编码不一致时，必须显式使用这两个类指定字符集，否则就会出现乱码。

装饰器模式：动态组合功能的艺术

观察 Java IO 的类图可以看到，FilterInputStream 派生出 BufferedInputStream、DataInputStream 等，它们都“包裹”着一个原始的 InputStream（如 FileInputStream）。这种结构正是装饰器模式的经典应用。
比方说dataInputStream(bufferedInputStream) 包裹层的这种组合体现了两种流的不同职责：

  • BufferedInputStream：负责传输效率，通过缓冲减少系统调用。
  • DataInputStream：负责数据解析，将字节解析为 int、long、UTF 字符串等 Java 基本类型。

优势：可以在运行时动态地为流叠加功能（如缓冲、数据解析），而无需为每一种功能组合创建大量子类。例如，new DataInputStream(new BufferedInputStream(new FileInputStream("data.bin"))) 既获得了缓冲的性能提升，又能直接读取 Java 基本类型。

性能与机制：缓冲流、readLine 隐患

缓冲流为什么快

没有缓冲的流（如 FileInputStream）每次调用 read() 都会直接触发操作系统的一次 系统调用（用户态切换到内核态），开销极大。而 BufferedInputStream 内部维护了一个字节数组作为缓冲区，当调用 read() 时，若缓冲区中有数据则直接返回；否则触发一次系统调用，将磁盘数据批量读入缓冲区，然后再返回第一个字节。

场景特征 推荐方案
处理文本文件，需要按行读取 BufferedReader + InputStreamReader (更推荐) 或 InputStreamReader + BufferedInputStream
处理二进制文件或自定义格式 BufferedInputStream
需要直接读取 Java 基本类型（int, long 等） DataInputStream + BufferedInputStream
追求极简且无需按行解析 Files.readAllBytes()（小文件）或 BufferedInputStream（大文件）

性能提升的本质：用空间换时间，将多次小批量 I/O 合并为一次大批量 I/O，大幅减少上下文切换次数。

BufferedReader的read() 与 readLine() 的区别及隐患

read() 返回 -1 表示结束，readLine() 返回 null 表示结束。

  • readLine() 的隐患：BufferedReader.readLine() 内部会逐字节判断换行符，并动态构建 String。如果一行数据非常大（例如几 MB），就会创建一个大对象，频繁触发 Young GC，甚至导致内存溢出。因此，在处理超大行数据时，建议使用 Scanner 或手动解析 char 数组。
  • read(byte[] b) 的效率优势：批量读取数据到自定义缓冲区，比逐字节 read() 或逐行 readLine() 更高效且可控。

底层原理：编码转换、IO 模型的演进、零拷贝

编码转换的具体过程

  • JVM 内部统一使用 UTF-16（即 Unicode）存储字符串。
  • 当从文件读取字节时，InputStreamReader 根据指定的字符集（如 UTF-8）将字节解码为 Unicode 字符，存入内存。
  • 当写入文件时，OutputStreamWriter 再将 Unicode 字符按目标字符集编码为字节。
  • 除了少部分生僻字占两个char外，其余的中英文都是占用一个char，也就是2个字节=16位。需要避免逐 char 打印，使用行读取或字符数组批量读取

常见的场景：
如果文件是 UTF-8 编码，但系统默认编码是 GBK，直接使用 FileReader（默认使用系统编码）会乱码，原因是FileReader 内部使用系统默认编码，此时会将 UTF-8 字节按 GBK 规则解码，导致乱码。必须显式使用 InputStreamReader 并指定 StandardCharsets.UTF_8。

从 BIO 到 NIO：IO 模型的演进

传统的 FileInputStream 属于 BIO（同步阻塞 I/O），每个连接对应一个线程，在高并发网络场景下会引发严重的线程资源消耗。Java 1.4 引入了 NIO（New I/O），核心组件是 Channel、Buffer 和 Selector（多路复用器）。

  • BIO 的问题：线程与连接数线性增长，上下文切换开销大，难以应对 C10K 问题。
  • NIO 的优势：一个线程通过 Selector 管理多个 Channel，只有当某个 Channel 有数据可读/可写时才进行处理，实现了 I/O 多路复用，极大地提升了并发能力。

零拷贝（Zero-Copy）技术

在文件传输场景（如 Web 服务器发送静态文件）中经常用到零拷贝技术，有两个使用案例：

  1. 在spring boot中用FileSystemResource返回文件内容，则Spring 底层会自动利用容器的零拷贝机制（如 Tomcat 的 sendfile 支持）
  2. NIO 的 FileChannel.transferTo() 方法正是利用操作系统的 零拷贝 特性（如 Linux 的 sendfile 系统调用），数据直接在内核空间完成传输，避免了用户态与内核态之间的 CPU 拷贝，显著降低 CPU 占用并提升吞吐量。

    Kernel->>Kernel: CPU 拷贝 (用户缓冲区→socket 缓冲区)
    Kernel->>Disk: DMA 拷贝 (socket 缓冲区→网卡)
    Disk-->>Kernel: 完成
    Kernel-->>App: 返回
    Note right of App: 4 次拷贝 (2 次 DMA + 2 次 CPU)<br/>4 次上下文切换

    Note over App,Disk: 零拷贝方式 (sendfile)
    App->>Kernel: sendfile() 系统调用
    Kernel->>Disk: DMA 拷贝 (磁盘→内核缓冲区)
    Disk-->>Kernel: 数据
    Kernel->>Kernel: CPU 拷贝 (内核缓冲区→socket 缓冲区)<br/>(或使用 scatter-gather 避免)
    Kernel->>Disk: DMA 拷贝 (socket 缓冲区→网卡)
    Disk-->>Kernel: 完成
    Kernel-->>App: 返回
    Note right of App: 2~3 次拷贝 (2 次 DMA + 0~1 次 CPU)<br/>2 次上下文切换
