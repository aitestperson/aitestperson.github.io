JVM 原理深度解析

前言

JVM（Java Virtual Machine）是 Java 技术的核心。它屏蔽了底层硬件和操作系统的差异，让 Java 程序能够实现「一次编写，到处运行」。理解 JVM 的运行原理，不只是为了排查问题和优化性能，更是为了真正理解 Java 程序是如何运行起来的。

JVM 不仅仅是一个执行引擎，更是一套完整的运行时环境。它管理着内存分配、垃圾回收、线程调度、类加载等核心功能。深入理解这些机制，能帮助我们写出更高效的代码，也能让我们在排查线上问题时有的放矢。

2.4 方法区

方法区是 JVM 规范中的逻辑概念。在 HotSpot 虚拟机中，JDK 8 之前主要由永久代实现，JDK 8 之后改为元空间（Metaspace）实现，并使用本地内存。

存储内容：

  • 类的元数据（Class 对象）
  • 常量池（运行时常量 + 符号引用）
  • 静态变量
  • JIT 编译器编译后的代码缓存

3.2 双亲委派模型（类加载器）

委派流程：

为什么要双亲委派？

  • 安全：防止核心类被篡改（自定义 String 类不会被加载）
  • 避免重复：父加载器已加载的类，子加载器不再加载
  • 保证一致性：类只加载一次，全局唯一

补充理解：JVM 创建对象时，并不是临时决定“该去哪个类加载器找类”，而是当前执行类在解析符号引用时，就已经通过自己的定义类加载器把目标类定位并加载好了。对象实例只是基于这个已经定义完成的类元数据创建出来的。对 JVM 来说，一个类的身份由“全限定类名 + 定义它的类加载器”共同决定。而在 java -jar 启动过程中，JVM 会通过 Launcher 初始化扩展类加载器和应用类加载器，并把应用类加载器设置为线程上下文类加载器，相关细节可查看《从 java -jar 到 main 方法执行发生了什么》。

3.3 破坏双亲委派

当默认的“先向上委派”规则无法满足需求时，比如要实现类加载隔离、SPI 扩展发现、热部署等能力，就需要调整默认的加载行为。这里所说的“破坏双亲委派”，并不一定意味着彻底推翻整个类加载器模型，更常见的是在特定场景下改变默认的查找路径。

常见方式主要有两类：

  1. 通过线程上下文类加载器反向加载

    • 代表场景：SPI、JDBC 驱动加载
    • 核心思想：不是让 BootstrapClassLoader 去硬加载业务类，而是借助当前线程的上下文类加载器，把核心库和业务实现连接起来

  2. 自定义 ClassLoader 并调整委派顺序

    • 代表场景：Tomcat、OSGi
    • 核心思想：通过重写 loadClass()，优先加载自身路径下的类，从而实现隔离、共存或热替换

四、垃圾回收基础

4.1 如何判断对象已死

算法有以下两种，而 JVM 中使用的是 可达性分析算法：
引用计数算法：对象被引用一次，计数 +1，引用失效 -1。简单高效，但无法解决循环引用问题。
可达性分析算法：通过 GC Roots 向下搜索，路径称为「引用链」。不在引用链上的对象判定为可回收。

4.2 可作为 GC Roots 的对象

类型 示例
虚拟机栈中引用的对象 方法中局部变量、参数
本地方法栈中 JNI 引用的对象 Native 方法中的对象
方法区中静态变量引用的对象 static Object obj
方法区中常量引用的对象 final Object OBJ
JVM 内部引用 异常对象、Class 对象
同步锁持有的对象 synchronized(obj) 持有的对象

4.3 常见垃圾回收算法

算法 原理 优点 缺点 适用场景
标记-清除 标记存活对象，清除未标记对象 简单 产生内存碎片 老年代
复制 将存活对象复制到另一半空间 无碎片 浪费一半空间 新生代（Eden → Survivor）
标记-整理 标记后移动存活对象到一端 无碎片、不浪费空间 移动开销大 老年代

4.4 Young GC 与 Full GC

Young GC 的触发条件（范围：仅年轻代）

核心触发条件只有一个：

  • Eden 区空间不足：当线程要在 Eden 区分配一个新对象，但 Eden 区剩余空间不足时，JVM 就会触发 Young GC。

这地方容易误解的点是：不是说 Survivor 区满了就会触发，它是 Young GC 的搬运目标，不是触发的扳机。

Full GC 的触发条件（范围：整个堆 + 方法区）

Full GC 是一次全堆级别的回收，代价高昂，通常只会在系统压力较大或某些特殊条件下触发。对大多数业务系统来说，最常见的触发原因主要有以下几类：

分类 具体触发条件 说明
空间不足 老年代空间不足 Young GC 后对象晋升失败，或大对象分配时老年代放不下
空间不足 元空间（Metaspace）不足 类加载过多，或大量动态代理、反射导致元空间被撑满
显式触发 调用 System.gc() 默认情况下可能触发 Full GC，可用 -XX:+DisableExplicitGC 禁用
收集器退化 CMS / G1 回收失败 比如 CMS 的 Concurrent Mode Failure，或 G1 疏散失败

可以把它理解为一句话：当 JVM 发现局部回收已经无法解决问题，或者运行时被显式要求做一次彻底清理时，就可能触发 Full GC。

4.5 GC 回收的过程

堆的回收流程

Young GC 的核心不是只处理 Eden，而是会把 Eden 和当前正在使用的 Survivor 区 中的存活对象，一起复制到另一个 Survivor 区。复制完成后，原来的 Survivor 区会被清空，两个 Survivor 区在下一次 GC 中继续轮换。

晋升到老年代的常见条件

  1. 对象年龄达到阈值
  2. 大对象直接进入老年代
  3. 动态年龄判断触发提前晋升

其中动态年龄判断的意思是：如果某一批相同年龄对象的总大小已经超过 Survivor 区空间的一半，那么这些对象以及年龄更大的对象，可以不必等到默认阈值就直接晋升到老年代。

方法区的回收流程

方法区的回收条件比较苛刻，主要回收两类内容：

  • 废弃常量
  • 不再使用的类

它通常不会像新生代那样高频发生，而更常见于 Full GC 或类卸载场景。

5.2 三色标记法

三色标记法是并发标记时使用的算法，将对象分为三种颜色：

颜色 含义 说明
白色（White） 不可达 垃圾
灰色（Gray） 自身可达，但未扫描成员 中间状态
黑色（Black） 自身可达，成员也已扫描 存活对象

并发标记时的问题：

  1. 漏标：本来存活的对象被错标为垃圾

  2. 错标：本来可回收的对象被标为存活（影响不大，只是这次不回收）

总述

JVM 的核心是内存管理与执行引擎。

内存管理解决的是「对象从创建到销毁」的全生命周期问题：通过可达性分析判断存活，通过分代回收提升效率，通过各种垃圾收集器平衡吞吐量与停顿时间。

执行引擎解决的是「字节码如何变成机器码」的问题：解释器即时解释执行，JIT 编译器热点代码编译优化，共同实现高性能。

理解这些底层机制，能让我们写出更高效的代码，也能在系统出现问题时快速定位根因。

延伸思考

1. 为什么新生代用复制算法，老年代用标记-整理？

  • 新生代：对象存活时间短，98% 都是朝生夕死，复制开销小
  • 老年代：对象存活时间长，复制成本高，整理可以释放连续空间

2. G1 为什么不叫「收集器」而叫「垃圾优先」？

G1 把堆划分成多个大小相等的 Region，每次回收优先级最高的Region（垃圾最多）。这是一种「化整为零」的思想，比整代收集更灵活。

3. ZGC 和 Shenandoah 的特点

收集器 目标 特点
ZGC 低延迟 最大停顿 < 1ms，Concurrent，几乎不停顿
Shenandoah 低延迟 类似 ZGC，但不支持并行回收
G1 平衡 吞吐量 + 延迟兼顾

4. JIT 编译器优化

  • 方法内联：热点方法直接内联，减少调用开销
  • 逃逸分析：分析对象作用域，栈上分配替代堆分配
  • 常量折叠：编译时计算常量表达式
