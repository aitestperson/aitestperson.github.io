从 java -jar 到 main 方法执行发生了什么

前言

平时我们执行一个 Java 程序，往往只需要一条简单的命令：

但在这条命令背后，JVM 并不是立刻就去执行 main 方法。真正发生的过程要复杂得多：JVM 需要初始化类加载器体系、设置线程上下文类加载器、定位主类、加载主类，最后才会执行 main 方法。

理解这个过程，不仅能帮助我们更好地理解类加载机制，也能让我们看清楚 Spring Boot、SPI、自定义 ClassLoader 这些机制是如何建立在 JVM 启动流程之上的。

启动流程总览

详细解析

第一步：JVM 启动

当执行 java -jar 时，首先启动的是 JVM 进程本身，而不是你的业务类。JVM 会先完成自身初始化，然后建立最基础的类加载环境。

这一阶段最重要的事情是：

  • 启动 JVM 运行时
  • 建立核心类库加载能力
  • 为后续 Java 世界的启动做好准备

第二步：创建 BootstrapClassLoader

BootstrapClassLoader 是启动类加载器，由 C++ 实现。它负责加载最核心的 Java 类库，比如：

  • java.lang.*
  • java.util.*
  • java.io.*

这些类是整个 Java 世界运行的基础。如果没有启动类加载器，连 String、Object 这些最基础的类都无法使用。

第三步：加载 Launcher

在 HotSpot 体系里，JVM 会继续加载 sun.misc.Launcher。这个类可以理解为 Java 应用启动过程中的关键协调者。

它的核心职责包括：

  • 创建并初始化扩展类加载器（ExtClassLoader）
  • 创建并初始化应用程序类加载器（AppClassLoader）
  • 设置线程上下文类加载器
  • 管理安全管理器（SecurityManager）
  • 提供访问 Bootstrap ClassPath 的能力

第四步：Launcher 初始化类加载器体系

Launcher 初始化时，会依次创建扩展类加载器和应用类加载器。

其中：

  • ExtClassLoader：在早期 JDK 中负责加载扩展目录中的类库
  • AppClassLoader：负责加载 classpath 下的应用类，也就是绝大多数业务代码

  • JDBC SPI 加载驱动
  • ServiceLoader 加载实现类
  • 一些容器或框架在运行时加载插件类

第七步：执行 main 方法

当主类加载完成后，JVM 通过反射定位 main(String[] args) 方法，并开始执行应用程序入口逻辑。

到这一步，Java 程序才算真正开始运行。

Spring Boot 的特殊之处

普通 JAR 包通常在 MANIFEST.MF 中指定 Main-Class，JVM 会直接加载这个类并执行其 main 方法。

但 Spring Boot 可执行 JAR 稍有不同，它通常会配置：

  • Main-Class：org.springframework.boot.loader.JarLauncher
  • Start-Class：真正的业务启动类，比如 com.example.Application

也就是说，JVM 先启动的是 JarLauncher，再由 JarLauncher 去创建自己的类加载器并加载真正的业务主类。

为什么 Spring Boot 要自定义 ClassLoader

根本原因在于：Spring Boot 的可执行 JAR 不是普通的平铺 classpath 结构，而是把依赖 JAR 以嵌套 JAR 的方式打进了一个大 JAR 包里。

普通的 AppClassLoader 只能加载文件系统路径或普通 URL 上的类资源，它并不擅长处理这种“JAR 里面再套 JAR”的结构。因此，如果直接使用默认 AppClassLoader，JVM 并不能方便地从 BOOT-INF/lib/*.jar 这种嵌套位置加载依赖类。

所以 Spring Boot 需要自己做两件事：

  1. 识别可执行 JAR 的内部结构
  2. 把嵌套 JAR 中的类资源暴露给类加载器使用

这就是 LaunchedURLClassLoader 存在的意义。

Spring Boot 并没有破坏双亲委派

Spring Boot 虽然自定义了 ClassLoader，但它并没有破坏双亲委派机制。

原因很简单：它的自定义类加载器仍然是建立在现有父加载器体系之上的，并没有改写“先委派父加载器、父加载器找不到再自己加载”的基本顺序。

  • JDK 核心类仍然由 BootstrapClassLoader 加载
  • 常规应用类加载规则仍然遵循父加载器优先
  • Spring Boot 只是扩展了“自己加载资源的能力”，而不是改变了委派顺序

换句话说，Spring Boot 做的是增强类资源加载能力，而不是推翻双亲委派模型。

自定义 ClassLoader 的正确姿势

如果要自定义 ClassLoader，Java 官方更推荐重写 findClass()，而不是直接重写整个 loadClass()。

原因是：

  • 重写 findClass()，仍然能保留双亲委派机制
  • 重写 loadClass()，则意味着你要亲自控制整个委派顺序，更容易打破默认模型

因此，绝大多数场景下：

  • 想扩展加载逻辑：优先重写 findClass()
  • 想改变委派顺序：才考虑重写 loadClass()

总述

java -jar 的背后，不是“找到主类然后执行”这么简单，而是一整套 JVM 启动与类加载器初始化流程。

JVM 先建立核心类加载能力，再通过 Launcher 构建扩展类加载器和应用类加载器，随后设置线程上下文类加载器，最后才加载用户主类并执行 main 方法。

理解这个过程之后，很多平时看起来零散的知识点——比如双亲委派、线程上下文类加载器、SPI、Spring Boot 自定义类加载器——都会串成一条完整的线。

从这个角度看，Java 程序启动过程不仅是一个“入口执行”的问题，更是整个类加载体系开始工作的起点。

延伸思考

为什么线程上下文类加载器很重要

双亲委派模型解决的是“从上往下找不到时，自己再加载”的问题，但某些场景需要反过来：让核心类库去加载业务层提供的实现类。

这时线程上下文类加载器就成了关键桥梁。
